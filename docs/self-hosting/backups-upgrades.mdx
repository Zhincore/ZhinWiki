A usable recovery set includes Postgres and object storage from the same
operational window. A database dump without uploaded assets is incomplete. Keep
copies outside the live host and account, and prove restoration before relying
on them.

Run the commands on this page from the deployment directory after
`export COMPOSE_FILE=docker-compose.prod.yml`, so `docker compose` uses the
production stack. In a repository checkout, `docker-compose.yml` is the
source-build stack.

## Create a backup

Dump Postgres in custom format, then archive the bundled maxio volume:

```bash
mkdir -m 700 -p backups
STAMP=$(date +%Y%m%d-%H%M%S)
docker compose exec -T postgres pg_dump -U nibleaf -d nibleaf --format=custom > "backups/nibleaf-db-$STAMP.dump"
MAXIO_VOLUME=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -q maxio)")
test -n "$MAXIO_VOLUME" && docker volume inspect "$MAXIO_VOLUME" >/dev/null \
  && docker run --rm -v "$MAXIO_VOLUME":/data:ro -v "$PWD/backups":/backup alpine:3.22 tar czf "/backup/nibleaf-storage-$STAMP.tar.gz" -C /data . \
  || echo 'Stop: could not identify or archive the maxio volume.'
```

These commands find the volume mounted at `/data` in the running maxio container, so
they work with any Compose project name and stop if it cannot be identified. External
R2 or S3 buckets are not in this volume, so skip those lines and use provider versioning,
replication, or an independent bucket backup.

From a repository checkout, `./scripts/backup.sh` runs the same two steps and prunes
local backups after 14 days. The script is not a release asset, so a directory with
only the downloaded release files does not have it.

`.env` holds the secrets that make a restore usable, including the encryption keys
for Git and integration credentials. Keep a protected copy with its own access
control. Without those keys, stored credentials cannot be decrypted.

Ship both artifacts off-host with separate credentials and record identifiers,
sizes, timestamps, retention, and the application release.

## Test a restore

Never overwrite production for a drill. Create an isolated database, storage
target, and application origin, then restore into them. On a separate host with its
own stack, using the same `$STAMP`:

```bash
docker compose --profile admin stop app admin server worker \
  && docker compose exec -T postgres pg_restore -U nibleaf -d nibleaf --clean --if-exists < "backups/nibleaf-db-$STAMP.dump" \
  && MAXIO_VOLUME=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps --all -q maxio)") \
  && test -n "$MAXIO_VOLUME" \
  && docker volume inspect "$MAXIO_VOLUME" >/dev/null \
  && docker compose stop maxio \
  && docker run --rm -v "$MAXIO_VOLUME":/data -v "$PWD/backups":/backup alpine:3.22 sh -c "find /data -mindepth 1 -delete && tar xzf /backup/nibleaf-storage-$STAMP.tar.gz -C /data" \
  && docker compose up -d \
  || echo 'Stop: restore failed; do not start application services.'
```

Then verify projects, memberships, page trees, current drafts, ready deployments,
uploaded assets, authentication isolation, and public search.

Record elapsed time and every manual step. A backup job exit code without a
successful isolated restore is not recovery evidence.

## Upgrade a pinned release

Use only a tag listed on the [releases page](https://github.com/Zhincore/ZhinWiki/releases).
Read each intervening release note and check for
release-specific migration or configuration changes. Create and restore-test a
backup. Then:

1. Replace the Compose file with the copy from the target release. Keep
   `.env`, the Compose project name, and the volume names. A version-only change
   misses settings that the new Compose file passes to the services:

   ```bash
   VERSION=vX.Y.Z
   curl -fsSLo docker-compose.prod.yml "https://github.com/Zhincore/ZhinWiki/releases/download/$VERSION/docker-compose.prod.yml"
   ```

2. Set `NIBLEAF_VERSION` to the same existing release tag in `.env`:

   ```dotenv
   NIBLEAF_VERSION=vX.Y.Z
   ```

3. Pull and recreate the services:

   ```bash
   docker compose pull
   docker compose up -d
   ```

Confirm the image digest, migration log, service health, sign-in, one upload,
one publish, one search, and one public page.

### From v0.1.0

- **Tenancy.** The new Compose file defaults to `TENANCY=shared`. Set
  `TENANCY=independent` in `.env` to keep the v0.1.0 behaviour. See
  [run a shared instance](/self-hosting/configuration#run-a-shared-instance).
- **Change requests.** The `20261029120000_change_requests` migration turns every
  existing non-default branch into a draft change request. Pages on `main`
  become read-only in the editor; edits go through change requests.
- **Better Auth 1.7.14.** The `20261030120000_invitation_created_at` migration runs
  on start. Sign-in is refused when two `account` rows share a provider and
  account ID; this check must return no rows:

  ```bash
  docker compose exec -T postgres psql -U nibleaf -d nibleaf -c 'SELECT "providerId", "accountId", count(*) FROM account GROUP BY 1, 2 HAVING count(*) > 1;'
  ```

- **AI provider.** The Compose file now passes `OPENROUTER_API_KEY` instead of
  `OPENAI_API_KEY`.
- **Worker queues.** If you set `WORKER_QUEUES`, add `erasure`, or the stored
  files of deleted projects stay in place.

## Roll back safely

Prisma migrations are forward-only. If no schema migration ran, pin the prior image,
restore the prior Compose file, and recreate the services. If a migration changed the
database, stop writes and restore the pre-upgrade recovery set before starting the
older application. Do not run the older application against the migrated schema.

Do not combine an application upgrade with a PostgreSQL major-version change.
Treat the database upgrade as a separate dump-and-restore project.
