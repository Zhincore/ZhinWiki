تتضمن مجموعة الاستعادة القابلة للاستخدام Postgres وتخزين الكائنات من النافذة
التشغيلية نفسها. وتُعد نسخة قاعدة البيانات من دون الأصول المرفوعة غير مكتملة.
احتفظ بنسخ خارج المضيف والحساب المستخدمين للخدمة الحية، وأثبت نجاح الاستعادة
قبل الاعتماد عليها.

نفّذ أوامر هذه الصفحة من مجلد عملية النشر بعد
`export COMPOSE_FILE=docker-compose.prod.yml`، ليستخدم `docker compose` منظومة
الإنتاج. أما في نسخة محلية من المستودع، فإن `docker-compose.yml` هو منظومة البناء
من المصدر.

## إنشاء نسخة احتياطية

أنشئ تفريغًا لـPostgres بالتنسيق المخصّص، ثم أرشف وحدة تخزين maxio المضمّنة:

```bash
mkdir -m 700 -p backups
STAMP=$(date +%Y%m%d-%H%M%S)
docker compose exec -T postgres pg_dump -U nibleaf -d nibleaf --format=custom > "backups/nibleaf-db-$STAMP.dump"
MAXIO_VOLUME=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps -q maxio)")
test -n "$MAXIO_VOLUME" && docker volume inspect "$MAXIO_VOLUME" >/dev/null \
  && docker run --rm -v "$MAXIO_VOLUME":/data:ro -v "$PWD/backups":/backup alpine:3.22 tar czf "/backup/nibleaf-storage-$STAMP.tar.gz" -C /data . \
  || echo 'Stop: could not identify or archive the maxio volume.'
```

تحدد هذه الأوامر وحدة التخزين المثبتة عند `/data` في حاوية maxio القائمة، لذا تعمل مع
أي اسم لمشروع Compose وتتوقف إذا تعذّر تحديدها. لا توجد حاويات R2 أو S3
الخارجية في هذه الوحدة، لذا تخطَّ هذه الأسطر واستخدم إمكانات المزوّد لإدارة
الإصدارات أو النسخ المتماثل، أو أنشئ نسخة احتياطية مستقلة للحاوية.

من نسخة محلية للمستودع، ينفّذ `./scripts/backup.sh` الخطوتين نفسيهما ويحذف النسخ
المحلية بعد 14 يومًا. لا يُعد هذا السكربت من أصول الإصدار، لذا لا يوجد في مجلد
يضم ملفات الإصدار المنزّلة فقط.

يحتوي `.env` على الأسرار التي تجعل الاستعادة قابلة للاستخدام، ومنها مفاتيح تشفير
بيانات اعتماد Git والتكاملات. احتفظ بنسخة محمية منه بتحكم وصول مستقل. فمن دون هذه
المفاتيح لا يمكن فك تشفير بيانات الاعتماد المخزنة.

انقل الملفين إلى خارج المضيف باستخدام بيانات اعتماد منفصلة، وسجّل المعرّفات
والأحجام والطوابع الزمنية وسياسة الاحتفاظ وإصدار التطبيق.

## اختبار الاستعادة

لا تستبدل بيئة الإنتاج مطلقًا عند إجراء تمرين. أنشئ قاعدة بيانات ووجهة تخزين
ومصدر تطبيق معزولة، ثم استعد النسخة فيها. على مضيف منفصل يملك منظومته الخاصة،
وباستخدام قيمة `$STAMP` نفسها:

```bash
docker compose --profile admin stop app admin server worker \
  && docker compose exec -T postgres pg_restore -U nibleaf -d nibleaf --clean --if-exists < "backups/nibleaf-db-$STAMP.dump" \
  && MAXIO_VOLUME=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' "$(docker compose ps --all -q maxio)") \
  && test -n "$MAXIO_VOLUME" \
  && docker volume inspect "$MAXIO_VOLUME" >/dev/null \
  && docker compose stop maxio \
  && docker run --rm -v "$MAXIO_VOLUME":/data -v "$PWD/backups":/backup alpine:3.22 sh -c "find /data -mindepth 1 -delete && tar xzf /backup/nibleaf-storage-$STAMP.tar.gz -C /data" \
  && docker compose up -d \
  || echo 'Stop: restore failed; do not start application services.'
```

ثم تحقق من المشاريع والعضويات وأشجار الصفحات والمسودات الحالية وعمليات النشر ذات
الحالة `READY` والأصول المرفوعة وعزل المصادقة والبحث العام.

سجّل الزمن المنقضي وكل خطوة يدوية. لا يُعد رمز خروج ناجح لمهمة النسخ الاحتياطي
دليلًا على قابلية الاستعادة من دون نجاح استعادة معزولة.

## ترقية إصدار مثبّت

استخدم فقط وسمًا مدرجًا في [صفحة الإصدارات](https://github.com/Zhincore/ZhinWiki/releases).
اقرأ ملاحظات كل إصدار وسيط، وتحقق من أي تغييرات خاصة بالإصدار
في الترحيل أو التهيئة. أنشئ نسخة احتياطية واختبر استعادتها. ثم:

1. استبدل ملف Compose بالنسخة من الإصدار الهدف. أبقِ `.env` واسم مشروع
   Compose وأسماء وحدات التخزين. لا يشمل تغيير الإصدار وحده الإعدادات التي يمررها
   ملف Compose الجديد إلى الخدمات:

   ```bash
   VERSION=vX.Y.Z
   curl -fsSLo docker-compose.prod.yml "https://github.com/Zhincore/ZhinWiki/releases/download/$VERSION/docker-compose.prod.yml"
   ```

2. اضبط `NIBLEAF_VERSION` في `.env` على وسم الإصدار الموجود نفسه:

   ```dotenv
   NIBLEAF_VERSION=vX.Y.Z
   ```

3. اسحب الخدمات وأعد إنشاءها:

   ```bash
   docker compose pull
   docker compose up -d
   ```

تحقق من ملخّص الصورة الرقمي، وسجل الترحيل، وسلامة الخدمات، وتسجيل الدخول،
وعملية رفع واحدة، وعملية نشر واحدة، وعملية بحث واحدة، وصفحة عامة واحدة.

### الترقية من v0.1.0

- **نمط المستأجرين.** يضبط ملف Compose الجديد `TENANCY=shared` افتراضيًا. اضبط
  `TENANCY=independent` في `.env` للإبقاء على سلوك v0.1.0. راجع
  [تشغيل مثيل مشترك](/ar/self-hosting/configuration#تشغيل-مثيل-مشترك).
- **طلبات التغيير.** يحوّل الترحيل `20261029120000_change_requests` كل فرع
  غير افتراضي موجود إلى طلب تغيير في حالة مسودة. تصبح صفحات `main` للقراءة فقط
  في المحرر، وتمر التعديلات عبر طلبات التغيير.
- **Better Auth 1.7.14.** يعمل الترحيل `20261030120000_invitation_created_at`
  عند التشغيل. يُرفض تسجيل الدخول إذا تشارك صفّان في جدول `account` المزوّد
  ومعرّف الحساب نفسيهما، ويجب ألا يعيد هذا الفحص أي صف:

  ```bash
  docker compose exec -T postgres psql -U nibleaf -d nibleaf -c 'SELECT "providerId", "accountId", count(*) FROM account GROUP BY 1, 2 HAVING count(*) > 1;'
  ```

- **مزوّد الذكاء الاصطناعي.** يمرر ملف Compose الآن `OPENROUTER_API_KEY` بدلًا من
  `OPENAI_API_KEY`.
- **طوابير العامل.** إذا ضبطت `WORKER_QUEUES`، فأضف `erasure`، وإلا تبقى ملفات
  المشاريع المحذوفة في التخزين.

## التراجع الآمن إلى الإصدار السابق

ترحيلات Prisma أحادية الاتجاه. إذا لم يُنفّذ أي ترحيل للمخطط، فثبّت الصورة السابقة،
واستعد ملف Compose السابق، وأعد إنشاء الخدمات. وإذا غيّر ترحيل قاعدة البيانات، فأوقف
عمليات الكتابة واستعد مجموعة الاستعادة السابقة للترقية قبل تشغيل التطبيق الأقدم. لا
تشغّل التطبيق الأقدم على المخطط المرحَّل.

لا تجمع ترقية التطبيق مع تغيير الإصدار الرئيسي لـPostgreSQL. تعامل مع ترقية
قاعدة البيانات على أنها مشروع مستقل للتفريغ والاستعادة.
